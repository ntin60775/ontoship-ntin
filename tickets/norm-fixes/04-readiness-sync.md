# Ишью 04 — готовность ship не зависит от remote, remote — канал синхронизации

Источник: требование оператора 2026-11-23 в проекте `dealer-network-orders`:
шип-флоу должен полноценно работать без remote, и появление remote позже
должно учитываться. Прежняя норма (решение оператора 2026-11-18) делала
push частью готовности, а отсутствие remote — пробелом готовности; проход
по такой норме не считался полным.

Правка (решение оператора 2026-11-23, вне тикетного потока, как ишью
01/02/03): готовность = коммит в целевой ветке и зелёный контур; `origin` —
канал синхронизации, а не условие готовности. Раздел «Деградация без
remote» заменён разделом «Синхронизация»:

- `origin` есть — push обязателен и входит в готовность, PR и CI идут тем
  же каналом; недоступный push — остановка и вопрос оператору;
- `origin` нет — проход оканчивается локальным коммитом, в отчёте строка
  `sync: origin не настроен, N коммитов не отправлено`, PR-путь и CI
  помечаются «недоступны (origin нет)», тикет принимается автоприёмкой;
- `origin` появился позже — ближайший проход видит его и пушит
  неотправленные коммиты целевой ветки (догон), называя это в отчёте;
- проверка `git remote -v` — в каждом проходе, без памяти прошлых прогонов.

Носители: канон «Определение готовности» и «Три фазы», раздел «Принцип»
AGENTS.md, шаг 7 и «Синхронизация» ship, зеркало method-phases, спека
`workflow-skills` (ревизия 2026-11-23).
