# Правило качества: доказательство, планка, классы, цикл

Правило качества канона даёт тесту **ровно три** законные цели:

1. **Spec-тест** — доказывает пункт спеки: наблюдаемое поведение, которое
   заказал клиент; тест доказывает вместе с прочитанным артефактом. Здесь живут
   критерии приёмки.
2. **Инвариантный охранник** — защищает инвариант проекта: то, что не должно
   ломаться никогда, даже когда спека молчит.
3. **Target-тест** — воспроизводит реальный сбой (баг, инцидент,
   продакшн-отчёт). Он порождается **из сбоя**, а не из спеки: получив
   кодовую базу, исключение или симптом и место, агент пишет тест, который
   заставляет сбой произойти.

Тест без ни одной из трёх целей — сирота: его нельзя обосновать и нельзя
удалить по правилу. Тест-сироту не хранят: его удаляют при первом касании
решением оператора. Тест, который лишь пересказывает реализацию, не
доказательство.

Ожидаемое значение берётся из независимого источника — спеки, литерала или
разобранного примера — и никогда не пересчитывается тем же способом, что код.

## Артефакт доказательства

Доказательство — не сигнал, а сопоставление: наблюдаемый **артефакт** реальной
работы программы против **ожидания из спеки**. Прохождение теста говорит лишь
«не разошлось с ожиданием, которое зашил автор теста» — это сигнал к чтению
артефакта, не доказательство; доказательством становится вывод «поведение —
действительно то, что нужно», сделанный по самому артефакту.

**Законные носители**: автоматический прогон, вывод команды, строка лога,
файл, ручная проба с приложенным артефактом — скопированный вывод, карточка
прогона, снимок. «Я проверил» без артефакта — не доказательство; ожидание
ручной пробы берётся из спеки, как у автоматической.

**Разбор расхождений — точка остановки ship**. Каждое расхождение
ожидание/факт разбирается до merge:

- дефект → правка + target-тест;
- не дефект → записанный вывод «почему поведение правильное»;
- расхождений не было → строка «не было».

Неразобранное расхождение блокирует merge; «перепрогнал — позеленело» — не
разбор. Каждый новый юнит переносит это правило разбора в свои «Ограничения».

## Планка качества target-теста

Target-тест — доказательство, только если выполнено всё:

- **Реальный путь сбоя.** Сбой воспроизводится через реальную входную точку
  продукта; искусственное исключение (сырой null во внутренний метод,
  принудительный throw) — не воспроизведение. Если баг действительно внутри
  приватного шва, скажи это и обоснуй.
- **Red→green.** Тест падает на базовом коммите по правильной причине и
  проходит после исправления. Тест, который проходит до исправления, ничего
  не доказывает.
- **Стабильность и детерминизм.** Никакой зависимости от таймингов, сети,
  порядка или окружения; сбой — это баг, а не харнесс.
- **Читаемость.** Описательное имя, минимальная фикстура, параметры, которые
  читатель может объяснить. `testBug`/`boom` и загадочные блобы — дефект
  качества, а не сокращение.
- **Ревью.** Вторая пара глаз (человек или независимый агент) проверяет, что
  тест воспроизводит заявленный сбой, а не соседний или выдуманный.
- **Хранить, пока класс сбоя жив.** Когда класс багов исправлен навсегда или
  функция выведена из эксплуатации, удали target-тест, как любой устаревший
  spec-тест.

## Когда какой класс использовать

| ситуация | основной класс | заметки |
|---|---|---|
| Новое поведение с видимым клиенту контрактом | spec-тест | критерии приёмки; ожидаемые значения из спеки |
| Отчёт о дефекте, краш, регрессия, инцидент | target-тест | сначала воспроизведи, потом исправляй; планка выше |
| Инвариант проекта (безопасность, формат, совместимость, целостность данных) | инвариантный охранник | детерминированный, дешёвый, широкий |
| Логика без независимого оракула | никакой — сначала найди доказательство | тест, пересказывающий код, тавтологичен |
| Поведение UI/браузера | target или spec на уровне E2E | агент через MCP + скриншот; не написанный вручную безопасный путь |
| Производительность/масштаб | инвариантный охранник (бюджет) | бюджеты index/lint/map для движка |

**Каналы — инструменты, а не цели:** unit/contract, E2E/smoke, ожидаемый
вывод, записанное воспроизведение, браузер/снимок, производительность.
Target-тест может жить в любом канале; spec-тест обычно живёт в
unit/contract или E2E.

## Агентный цикл target-теста

1. **Воспроизведи** — получи тесную детерминированную команду, которая
   краснеет на заявленном сбое: названная команда, уже запущенная, которая
   умеет краснеть.
2. **Исследуй** — прочитай код и логи достаточно, чтобы назвать предусловие,
   которое вызывает сбой. Недостаточное исследование — крупнейший режим
   сбоя.
3. **Рассуди** — сформулируй механизм сбоя и ожидаемое наблюдение до
   написания теста.
4. **Набросай и запусти** — по одному тесту за раз, выполняй, уточняй; держи
   набор минимальным.
5. **Планка качества** — проверь пункты выше: реальный путь, red→green,
   стабильность, читаемость, ревью; отвергай вырожденные обходы и обходы
   через приватный API.
6. **Исправь** — исправление следует за воспроизведённым сбоем; target-тест
   остаётся регрессионным охранником.
7. **Диагностируй при неудаче** — если воспроизведения нет после бюджета,
   остановись и доложи, что пробовал и чего не хватает (окружение, артефакт,
   инструментация), а не пиши поверхностный тест.

Бюджет задай до цикла: генерация target-тестов не должна съесть сессию.
