# Skill: deliver
# Поставка и обновление OntoShip в проекте

Носитель интента «поставить/обновить OntoShip в проекте X»: полный
протокол поставки и обновления живёт здесь; блок входа init только
называет команду. deliver — весь акт поставки/обновления; init — точка
входа, его запускает deliver после установки. Скоуп — только ядро
OntoShip: паки стандартов, team-бандл и стек deliver не ставит и не
обновляет — это их контуры.

## Когда использовать

- Оператор просит поставить OntoShip в проект, обновить установку или
  командует «деплой и обновление [имя_проекта]».
- Интент сформулирован произвольно близко по семантике — понимай сразу,
  без гадания; имя проекта X бери из запроса.

## Протокол

1. **Источник.** deliver исполняется там, где чекаут ядра доступен:
   `scripts/install.sh` лежит в корне репо ядра, не в бандле.
   Link-продюсер резолвит путь ядра из realpath бандла
   `.agents/skills/deliver`; copy-продюсер — ask оператора о чекауте
   ядра. Молчаливого клона и remote нет — правило одного пути. Канал
   продюсера и путь использованного install.sh фиксируй в evidence.
2. **Поиск X.** имя → реестр потребителей и соседние чекауты; не найден
   — ask пути, не угадывай.
3. **Состояние.** `install.sh --check <X>` до обновления определяет
   состояние. Warning установщика (legacy-корни, выведенные бандлы)
   называй в отчёте до утверждения «поставлено»; `check: ok` не отменяет
   warning.
4. **Канал.** Свежая установка — ask канала link/copy; обновление —
   тем же каналом; смена канала — ask оператора, молча канал не
   меняется. Замена неверного симлинка в `.agents/skills/` — штатное
   действие установщика (relink), не деструктив.
5. **Установка/обновление.** install.sh соответствующего канала.
   Drifted-копия — отказ установщика «copy differs» называется,
   протокол останавливается на ask удаления: деструктив у потребителя
   — только с подтверждения оператора. Legacy-корни и выведенные
   бандлы установщик не трогает — называй и спрашивай.
6. **Init.** После свежей установки и при обновлении — скилл init:
   идемпотентен, блок входа — только между маркерами ontoship, текст
   вне маркеров не трогается. install.sh сам init не запускает.
7. **Акт rollout.** Коннектор — скилл реестра `consumer-registry`.
   Скилл в каталоге — загрузи его и следуй правилам: файла реестра нет
   — исполни старт ведения по правилам скилла (machine/project
   заполняются фактами), затем пиши акт. Скилла нет — запись не
   делается, пробел называется в финальном отчёте; fallback-записи в
   другой носитель нет. Реестр producer-side: deliver не ставит реестр
   потребителям и не требует его наличия. Факт rollout пишется только
   в реестр; continue.md целевого проекта deliver не пишет.
8. **Отчёт фактами.** Версия до/после, канал, вывод check, warning,
   акт или названный пробел — финальным сообщением сессии.

## Контракт акта

- `action` = `rollout` (свежая поставка) | `update` (обновление).
- `actor` = сессия deliver.
- `to`/`version` потребителя = тег link-дерева, иначе `git describe`
  (dev+sha); для copy — прежнее `consumers[].version`, без прежней
  записи — `unknown` с названным пробелом.
- `from` = прежнее `consumers[].version`.
- `updated_at` обновляется.
- Перед поставкой сверь открытые followups (`done: false`) по правилам
  скилла реестра; после обновления пиши followup «свежая сессия
  потребителя».
- `acceptance[]` deliver не заполняет — акт оператора, названный пробел
  v1.
- deployed.json не заводится.

## Границы

- Ask-ноги протокола (поиск X, удаление drifted-копии, смена канала,
  чекаут для copy-продюсера) исполняются только с ответом оператора;
  ответа нет — протокол стоит, нога называется пробелом.
- Отсутствие скилла реестра и отсутствие файла реестра — разные ветки:
  скилла нет — пробел; файл отсутствует при установленном скилле —
  старт ведения, затем акт.
