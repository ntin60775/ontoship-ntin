# Init

Настрой точку входа проекта OntoShip. Запускай это один раз на проект, после
установки ядра. Скилл **идемпотентен**: повторный запуск ничего не меняет, и
`git diff` после него пуст.

**Чем владеет init.** Четыре файла, ничего больше:

- `AGENTS.md` — управляемый блок между `<!-- BEGIN ontoship -->` и
  `<!-- END ontoship -->`. Всё вне маркеров — текст проекта: никогда не правь, не
  перемещай и не переписывай файл целиком.
- `.gitignore` — строки, которые требует харнесс: `.gitmark/`, `*-map.html`,
  `.scratch/`, строка навыкового корня; в DSH — четыре строки, в ZCode —
  те же шесть, что и раньше: добавляются `.zcode/agents/` (генерируемые
  определения ролей) и `.zcode/workflows/` (вендоренные файлы прогонов).
  Строка корня — `.agents/skills/` (установщик и плагин маркета v0.2.0+)
  или `.zcode/skills/` (legacy-канал v0.1.0) — скрывает project-local
  установку скиллов.
- `.agents/config.toml` — реестр ролей: одна секция `[agents.<роль>]` на роль
  с обязательным ключом `model`.
- `docs/ops/continue.md` — скелет состояния работы: init создаёт его, только
  когда файла нет; существующий файл init не открывает и не правит.

Init пишет эти четыре файла и ничего больше: он не создаёт индекс команд или
генерируемые таблицы, не пишет ничего в `docs/`, кроме скелета
`docs/ops/continue.md` при отсутствии файла, не пишет навыковые корни каналов,
`.gitmark/` или любой другой файл и не запускает `index`, `lint` или `map`.
Если он не может записать один из четырёх файлов, он сообщает об этом и
останавливается — он никогда не подменяет расположение.

## 0. Определи харнесс

Харнесс определяется доступным инструментом хоста, не путём и не файлом
проекта: `list_subagent_models` и `subagent` — DSH; `ListModels` — ZCode.
Ни одного или оба — задай вопрос оператору и остановись: харнесс не
угадывается, и ветки ниже не смешиваются.

## 1. Найди корень проекта

Запусти `git rev-parse --show-toplevel` из корня проекта; откатись к текущему
каталогу, когда проект не git-репозиторий. Пиши все четыре файла в этом корне.

`AGENTS.md` читается из корня проекта; харнесс может также смотреть родительские
каталоги и собственные глобальные файлы, но точка входа принадлежит корню проекта.
Не пиши глобальный `AGENTS.md` или вложенный `AGENTS.md`.

## 2. Обнови AGENTS.md

Прочитай файл **не нормализуя его байты** — бинарный ввод-вывод или текстовый с
`newline=''`. Определи стиль переводов строк по первой строке (`\r\n` или `\n`) и
используй его для вставленных строк. Маркер присутствует, только когда целая строка,
без учёта завершающего `\r`, равна строке маркера. Затем примени ровно один из пяти
случаев:

| случай | действие |
|---|---|
| `AGENTS.md` отсутствует | создай его, содержащим ровно блок выбранной ветки ниже |
| файл существует, ни одна строка маркера не встречается | добавь одну пустую строку, затем блок; каждая существующая строка остаётся |
| один BEGIN и один END, в этом порядке, и внутренний текст равен шаблону | ничего не меняй; файл уже актуален |
| один BEGIN и один END, в этом порядке, и внутренний текст отличается | замени только внутренний текст, сохрани строки маркеров и всё вне них; сообщи `[WARN]` |
| любая строка маркера встречается, но пара — не ровно один BEGIN, затем один END | ничего не меняй, сообщи `[FAIL]`, остановись — остальные файлы не трогай |

Последний случай покрывает одиночный маркер, перевёрнутую пару, дублирующую пару и
маркер, который стоит не на своей строке. Отказывай закрыто: догадка о том, какая
пара — «та самая», рискует уничтожить текст проекта.

Блок зависит от харнесса: DSH-ветка пишет блок DSH с командой `/ship`,
ZCode-ветка — блок ZCode. Каждый блок несёт единственный плейсхолдер
`<навыковый корень>`; остальное — дословно: не переформатируй, не
переименовывай, не добавляй и не удаляй строки.

**Блок DSH.**

````markdown
<!-- BEGIN ontoship -->
## База знаний (OntoShip)

- Точка входа: [`docs/README.md`](docs/README.md) — главный индекс KB; у каждой папки
  есть индекс `README.md`.
- Ищи до ответа или записи: загрузи скилл `kb-search`. Движок лежит в
  `<навыковый корень>/kb-search/gitmark.py`; корень — `.agents/skills`.
- Новые или обновлённые документы: загрузи скилл `kb-curate` — сначала поиск, никогда
  не дублируй.
- Сопровождение после правки документов:

  ```sh
  python3 <навыковый корень>/kb-search/gitmark.py index
  python3 <навыковый корень>/kb-search/gitmark.py lint --strict
  python3 <навыковый корень>/kb-search/gitmark.py map -o docs-map.html
  ```

- KB — это markdown + git: `.gitmark/`, `*-map.html` и `.scratch/` производные или
  эфемерные — никогда не коммитятся.

## Вход в работу (OntoShip)

- Изменения этого проекта идут через ship-флоу: скилл `ship` вызывается
  командой `/ship`, один тикет за запуск; свободные правки в обход тикета
  не делаются — прямые решения оператора выше этого правила.
- Запрос плана открывает draft-спеку через скилл `grilling`; режим плана
  харнесса (в ZCode — план-мод) не используется.
- Состояние и порядок работы — [docs/ops/continue.md](docs/ops/continue.md):
  сессия продолжается оттуда и берёт следующий тикет оттуда же.
- Команды: «стартуй юнит» — открыть draft-спеку; `ship` — командой
  `/ship` или «исполняй тикет N».
<!-- END ontoship -->
````

- Новые или обновлённые документы: загрузи скилл `kb-curate` — сначала поиск, никогда

## Вход в работу (OntoShip)

- Изменения этого проекта идут через ship-флоу: скилл `ship` по команде
  оператора, один тикет за запуск; свободные правки в обход тикета не
  делаются — прямые решения оператора выше этого правила.
- Запрос плана открывает draft-спеку через скилл `grilling`; режим плана

- Состояние и порядок работы — [docs/ops/continue.md](docs/ops/continue.md):
  сессия продолжается оттуда и берёт следующий тикет оттуда же.
- Команды: «стартуй юнит» — открыть draft-спеку; «исполняй тикет N» — ship

Блок выбранной ветки — генерируемое содержимое. Инструкции конкретного
проекта принадлежат вне маркеров. `<навыковый корень>` — плейсхолдер:
подставь корень канала установки, где стоят бандлы проекта: в DSH —
`.agents/skills`, в ZCode — `.agents/skills` или `.zcode/skills`. Копия
бандла вне проекта (кэш маркета, исходный checkout) корнем не считается —
смотри, куда установлены скиллы, и назови выбор в отчёте. Подстановка — при
сравнении и при записи; во всём остальном блок дословный, не переформатируй
его. Правка внутри блока теряется при следующем init; скажи об этом, когда
блок заменяется.

Сравнивай внутренний текст после нормализации переводов строк (`\r\n` → `\n`) с обеих
сторон, чтобы файл с CRLF и в остальном актуальным блоком не переписывался. При
записи сохраняй каждый байт вне блока как был; не добавляй завершающий перевод
строки, которого в файле не было.

## 3. Обнови .gitignore

Создай файл, если его нет. Иначе добавь только строки, которых ещё нет как
строки (сравнивай обрезанную строку). Оставь каждую существующую строку, её
порядок и комментарии — никогда не удаляй дубль, более широкий шаблон или
комментарий. Добавляй отсутствующие строки в этом порядке; набор зависит от
харнесса.

**DSH — четыре строки.** `.zcode/agents/` и `.zcode/workflows/` не нужны:
сгенерированных определений ролей и вендоренных прогонов в DSH нет.

```text
.gitmark/
*-map.html
.scratch/
<навыковый корень>/
```

**ZCode — шесть строк.** К четырём строкам добавляются определения ролей и
вендоренные прогоны.

```text
.gitmark/
*-map.html
.scratch/
<навыковый корень>/
.zcode/agents/
.zcode/workflows/
```

Если файл непустой и не заканчивается переводом строки, добавь его перед
добавлением. Заверши переводом строки после последней добавленной строки.
Если все строки набора уже есть, ничего не меняй.

## 4. Создай скелет continue.md

`docs/ops/continue.md` — состояние работы проекта: сессия продолжается от
этого файла. Файла нет — создай каталог `docs/ops` и запиши в него файл
`continue.md`: тело ниже дословно, единственная подстановка — сегодняшняя
дата в формате YYYY-MM-DD вместо `<дата>` в поле `updated`; отчёт называет
`created`.

Файл существует — не правь его ни байта: отчёт называет `unchanged`, и init
переходит к следующему шагу. Содержимое существующего файла принадлежит
проекту: расхождение с шаблоном — не дефект, последующие запуски init его
не читают и не меняют.

```markdown
---
node_type: runbook
title: Продолжение работы над проектом
service: _platform
status: active
updated: <дата>
---

# Продолжение работы над проектом

Это канонический старт каждой сессии. Источник истины — этот файл и тикеты,
не память сессии.

## Состояние

Где проект: закрытые юниты и тикеты, открытый юнит, последний merge.

## Открытая работа

Что исполняется: юнит, тикет, на чём остановились, что дальше.

## Порядок тикетов

Юниты и тикеты в порядке исполнения; блокировки отмечены.

## Что осталось

Отложенная работа: пункт с условием возврата.

## Стартовый промпт

Текст, с которого открывается сессия. Чек-лист фазовых переходов:
вычитка спеки перед план-гейтом — скилл `grilling`; критик после нарезки —
скилл `to-tickets`; ревью-панель перед merge — скилл `ship`.
```

## 5. Бутстрап ролей

`<корень>/.agents/config.toml` — реестр ролей: одна секция `[agents.<роль>]`
на роль, обязательный ключ `model`.

**Конфиг существует.** Не трогай его — идемпотентность не врёт.
Сверь роли ядра — `reviewer-spec`, `reviewer-tests`, `reviewer-code`,
`reviewer-kb`, `critic`, `curator` — с секциями конфига. Роль ядра без секции —
назови пропуск в отчёте и предложи добавить секцию; молча не дописывай.
Незнакомые секции и ключи в ZCode назовёт генератор предупреждением; в DSH
генератора нет — назови их в отчёте, конфиг не правь.

**Конфига нет — бутстрап.** Источник моделей и запись конфига зависят от
харнесса; вопрос о модели каждой роли общий.

1. Получи активные модели штатным инструментом харнесса (ветки ниже). Нет
   инструмента или список пуст — назови пробел и остановись: имена моделей
   не угадываются.
2. Спроси модель каждой роли ask-инструментом; в вариантах давай только
   активные модели, рекомендацию первой. Ревью-роли могут делить одну
   модель: независимость ревью — отдельный контекст субагента, не отдельная
   модель. Модель роли `critic` рекомендуется отличной от модели сессии;
   совпадение, в том числе явное, допустимо — назови его в отчёте, отказом
   оно не является.
   Отдельный вопрос — модель роли `curator`. Рекомендация — дефолт куратора
   `account:zai-individual-coding-plan/GLM-5.3-Flash`: рекомендуй её только
   пока она в списке активных; иначе рекомендуй ближайшую активную модель
   и назови отклонение от дефолта.
3. Запиши конфиг: по секции на каждую роль, `model = "<выбранная модель>"`
   и `level = "<уровень>"`. Уровень берёт из стандартной раскладки
   харнесса, когда она задана; иначе бери
   максимум из доступных уровней выбранной модели. Источник уровней —
   тот же список активных моделей шага 1.
   У модели без уровней ключ `level` опусти.

### DSH

1. Источник — `list_subagent_models`: без аргументов — провайдеры, с
   провайдером — модели, с провайдером и моделью — уровни. Маршрут роли —
   строка `<provider>/<model>`.
2. **Стандартная раскладка.** Роли ядра поставляются одной раскладкой:

   | роль | `model` | `level` |
   |---|---|---|
   | `reviewer-spec`, `reviewer-tests`, `reviewer-code`, `reviewer-kb` | `qwen-token-plan/qwen3.8-flash` | `xhigh` |
   | `critic` | `qwen-token-plan/qwen3.8-max` | `medium` |
   | `curator` | `qwen-token-plan/qwen3.8-flash` | `xhigh` |

   Сверь её с живым каталогом: все шесть маршрутов и их уровни доступны —
   запиши её без ask. Хоть один маршрут или уровень недоступен — спроси
   оператора: в вариантах только активные пары, ближайшая к стандарту
   первой; назови отклонение от стандарта в отчёте.
3. Модель сессии возьми из runtime-контекста («powered by <модель>»). Строка
   недоступна или неоднозначна — спроси оператора; источника нет — назови
   пробел и остановись.
4. Отсутствие ключа `level` — штатный дефолт модели; назови его в отчёте.
5. Сгенерированные определения ролей не нужны: DSH читает реестр в момент
   запуска. `gen_agents.py` не запускай; `.zcode/agents/` и
   `.zcode/workflows/` не создавай.

### ZCode

1. Источник — `ListModels`; модель сессии в списке помечена `[current]`.
2. Маршрут роли — идентификатор модели ZCode из списка.
3. Запусти генератор определений из корня проекта — генератор стоит в этом
   же бандле:

   ```sh
   python3 <навыковый корень>/init/gen_agents.py <корень проекта>
   ```

   Определения пишет генератор, не ты; вручную их не редактируют. Хост
   увидит новые роли после своего перезапуска.

## 6. Проверь

Из корня проекта:

```sh
git diff -- AGENTS.md .gitignore .agents/config.toml docs/ops/continue.md
git status --short
```

Первый прогон: `git status --short` называет созданные (`??`) и изменённые
(`M`) файлы; diff показывает блок, отсутствующие строки, новый конфиг и новый
скелет — для новых файлов diff пуст, пока файл не в индексе или коммите.
Второй прогон: **никаких изменений** — ни нового diff, ни новых строк в
`git status --short`. Это и есть проверка идемпотентности, а не утверждение.
Если второй прогон что-то меняет, текст блока, сравнение строк, запись
конфига или запись скелета нестабильны: исправь скилл, не замазывай.

Проверь, что пара маркеров ровно одна:

```sh
grep -c '^<!-- BEGIN ontoship -->$' AGENTS.md   # 1
grep -c '^<!-- END ontoship -->$' AGENTS.md     # 1
```

## 7. Отчёт

Назови каждый файл и что произошло: `created`, `appended` (назови строки),
`updated inside markers` или `unchanged`. Для `docs/ops/continue.md` итог —
`created` или `unchanged`; содержимое существующего файла в отчёт не входит.
При обновлении предупреди, что правки внутри блока не выживают. При `[FAIL]`
процитируй проблему маркеров и заяви, что ничего не изменено. Для конфига
назови итог: записанные роли и их модели, либо пропуски ролей ядра, либо
пробел источника моделей. В DSH генератор не запускается и перезапуск хоста
не нужен; в ZCode доложи вывод генератора и напомни про перезапуск хоста.

Затем передай дальше: следующий шаг — построить KB. `docs/README.md` — главный индекс;
новые документы идут через `kb-curate`; команды сопровождения — в блоке. Не запускай
их в рамках init.
