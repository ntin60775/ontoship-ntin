# Онто-док: сборка KB целиком

Построй (или пересобери) **всю базу знаний** этого репозитория fan-out'ом
кураторов. Область приходит из разговора: весь репозиторий или подмножество
(например `services/api services/billing` или «только reference-доки»).

## Шаги

1. **Обследуй репозиторий** — составь карту верхних каталогов, сервисов и
   модулей, точек входа, build/deploy-файлов и существующих доков. Проверь
   текущее покрытие: `python3 skills/kb-search/gitmark.py stat`.

2. **Разбей на док-области** — один кусок работы на область:
   - каждый сервис или компонент → `docs/services/<svc>/README.md`
     (`node_type: service`);
   - сквозные спеки (архитектура, биллинг, лимиты, безопасность) →
     `docs/reference/` (`reference`);
   - операционные процедуры → `docs/ops/` (`runbook`; `gotcha` — рядом с тем,
     о чём предупреждает);
   - архитектурные решения → `docs/decisions/` (`decision`).

3. **Запусти кураторов (fan-out)** — на каждую область работает куратор
   транспортом харнесса и ведёт свой срез строго по скиллу `kb-curate`:
   - сначала поиск (не дублируй); выбери `node_type` и правильную папку;
   - напиши frontmatter (`node_type`, `title`, `service`,
     `status: active`, `updated`);
   - добавь хотя бы одну типизированную ссылку на документируемый код
     (`documents:[src/…]` / `implemented_by`);
   - добавь строку в `README.md`-индекс папки.
   Запускай независимые области параллельно; держи каждого куратора в его
   области, чтобы кураторы не спорили за файлы. Запуск — процедурой
   «Запуск прогона» ниже: план кусков `[{path, what}]`, по куратору на кусок;
   отчёт прогона прочитай до следующего шага.

4. **Точка входа и индексы** — проверь, что `CLAUDE.md` / `AGENTS.md`
   существуют как точка входа, `docs/README.md` — главный индекс и у каждой
   папки есть README-индекс. Итог проверки — в отчёт; запись точки входа —
   домен скилла `init`.

5. **Проверь и выведи производное** —
   `python3 skills/kb-search/gitmark.py lint` (исправь битые ссылки, сирот,
   пропавший frontmatter), затем `... gitmark.py index`, затем
   `... gitmark.py map -o docs-map.html`.

6. **Отчёт** — сколько документов создано и обновлено, покрытие KB до→после,
   итог lint и путь карты. Перечисли области, требующие решения человека.

## Запуск прогона

1. Сверь роль куратора: прочитай `model` и `level` из `[agents.curator]`
   в `.agents/config.toml`; `level` необязателен: в DSH отсутствие —
   штатный дефолт модели с пометкой в отчёте, в ZCode — максимум из
   доступных. Сверь модель и уровень с каталогом моделей хоста — в DSH
   `list_subagent_models`, в ZCode `ListModels`: модель должна
   присутствовать, уровень — входить в её доступные уровни.
   Расхождение — стоп. Каталога нет — названный пробел и стоп, не
   угадывание.
2. Запусти сохранённый workflow или fan-out `subagent`. ZCode — сохранённый
   workflow `onto-doc` с тремя аргументами: `root` (корень KB — worktree
   прогона), `plan` (куски декомпозиции) и `model` (назначенная модель —
   файл прогона печатает её в log). DSH — fan-out `subagent` (spawn, не
   `subagent_fork`): по куратору на кусок, все кураторы стартуют в одном
   сообщении с `provider`, `model` и `reasoning_effort` из
   `[agents.curator]`; `workflow` не используется — его `agent()` не несёт
   `effort`. План проверяет родитель до fan-out: путь относительный, без
   `..` и без начального `/`, области не повторяются, пустой план — стоп.
   Каждый куратор возвращает только JSON-строку с полями `path`, `curator`,
   `files` и `refusal`; ответ не по схеме — именованный отказ строки, а не
   пустой список. Транспорт модели и уровня — свой у каждого харнесса;
   процедура — в разделе «Прогон онто-дока по харнессам» файла
   `references/ontodoc-run.md` этого бандла. Файл бандла — первоисточник;
   проект переопределяет его документом `docs/reference/ontodoc-run.md` —
   написал свой, бери его. Прогон пишет только внутри `root`.
3. Прочитай отчёт прогона: строку на область — куратор, файлы, отказ.
   Сверь карточку с фактом до отчёта оператору: индексируй правки
   (`git add -A`) и сверь объединение `files` всех строк с
   `git diff --cached --name-only` в корне прогона; пустой `files` при
   непустом diff — расхождение; лишний `files` — тоже; разбор — правилом
   «Артефакт доказательства» в `../testing/references/quality-rule.md`.
   Файл бандла — первоисточник; проект переопределяет его документом
   `docs/reference/quality-rule.md` — написал свой, бери его.
   Карточку на веру не принимай.

После project-local установки движок лежит в навыковом корне канала:
`.agents/skills/kb-search/gitmark.py` или `.zcode/skills/kb-search/gitmark.py`;
используй путь твоего канала вместо `skills/kb-search/gitmark.py`.

Принцип: md+git — источник истины; производное (индекс, граф)
перегенерируется. Не дублируй — правь существующие документы. Держи кураторов
в их областях, чтобы они не спорили за файлы.
