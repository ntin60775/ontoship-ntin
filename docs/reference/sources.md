# Источники основной идеи

Ядро — композиция трёх источников. Эта страница фиксирует, что каждый из них на
самом деле говорит, что было взято и что сознательно оставлено. Все три под MIT.

## 1. OntoShip — KB + dev-flow

[vakovalskii/ontoship](https://github.com/vakovalskii/ontoship) ·
[dev-flow skill](https://github.com/vakovalskii/ontoship/blob/main/skills/dev-flow/SKILL.md) ·
[positioning ADR](https://github.com/vakovalskii/ontoship/blob/main/docs/decisions/ontoship-positioning.md)

- **Идея:** markdown + индекс `README` + git. Всё производное (индекс, HTML-граф,
  реестры) перегенерируется. Один самодостаточный CLI на Python stdlib. Онтология
  необязательна: «Use it or ignore it; the tool doesn't force it».
- **Доказательство существованием:** на живом проекте 421 документ, 568 ссылок, 88
  README, 617 коммитов KB; `gitmark index` пересобирается за 1,5 с при ~50 МБ RAM.
- **dev-flow:** исследование → задачи → цель → спека (markdown в KB) → worktree →
  реализация → тесты → независимое ревью → dev-тесты → prod-тесты → ship. Примерно
  от 40 минут до 2 часов; независимый ревьюер поймал 191 баг до прода.
- **Позиционирование:** продукт — workflow (оператор + агент → PR), а не поиск. Цель —
  передача: новый оператор доходит до PR без автора в контуре.

**Взято:** KB как субстрат, скелет dev-flow, worktree, независимое ревью,
позиционирование «продукт — это workflow», свойство простоты и метрика передачи
(новый оператор → первый PR без автора).

**Оставлено:** обязательная онтология, реестр планов и команд как гейт и идея, что
каждую деталь процесса нужно записать прозой.

## 2. Matt Pocock — grilling и to-tickets

[mattpocock/skills](https://github.com/mattpocock/skills) ·
[grilling skill](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md) ·
[to-tickets skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md)

- **grilling:** разложи предмет как дерево дизайна; каждый раунд спрашивает весь
  **фронтир** (решения, чьи предпосылки улажены), нумерует вопросы и даёт к каждому
  рекомендованный ответ. **Факты — работа агента; решения — пользователя.** «An agent
  running grilling that answers its own decisions has broken the skill». Готово, когда
  фронтир пуст и пользователь подтвердил общее понимание.
- **to-tickets:** tracer-bullet вертикальные срезы, каждый можно показать, у каждого
  есть блокирующие рёбра; квиз перед публикацией; локальные файлы в
  `.scratch/<feature>/issues/` или реальный трекер; никаких якорей `file:line` (они
  устаревают); критерии приёмки должны падать на базовом коммите.
  `disable-model-invocation: true` — агент никогда его не вызывает.

**Взято:** механизм интервью и разделение фактов и решений; tracer-bullet, блокирующие
рёбра, квиз, демо-путь и правило «критерии должны падать на базе»; тикеты как
эфемерные артефакты исполнения.

**Оставлено:** инверсии форка zcode — автономный grilling, автоматическая цепочка
grilling → to-tickets, тикеты в KB с машиной статусов и реестром планов.

## 3. Стратегия тестирования оператора

Записана в исследовательской заметке от 2026-10-19; утверждения ниже принадлежат
оператору.

- **Цель:** тест доказывает **пункт спеки** (то, что заказал клиент) или охраняет
  **инвариант проекта**. Ничто другое тест не обосновывает.
- **Тестирование от доказательства:** `spec → invariant → proof → test`, а не
  `spec → test`. Ожидаемое значение берётся из независимого источника (спека,
  литерал, разобранный пример) и никогда не пересчитывается тем же способом, что код.
- **Unit-тесты — дым:** модель редко ошибается в логике алгоритма; сбои живут на
  границах развёртывания, версий и интеграций. Тестируй логику, где есть
  доказательство или инвариант, а не «на всякий случай».
- **Браузер/E2E создаёт новый контекст:** скриншоты и реальное состояние UI — это
  информация, которой нет у кода и логов. Бэкенд-тесты часто дублируют логи.
- **Написанный вручную сценарный E2E — ловушка безопасного пути:** он растёт быстрее
  кода, а качество не следует. Сценарии принадлежат **агенту через MCP**, который
  действует как пользователь; агент читает логи и код, а его главный продукт —
  **диагностический отчёт** с проблемным срезом данных; кодирующая LLM исправляет по
  нему за один заход.
- **Агентный E2E дополняет детерминированные проверки**, а не заменяет их; агент
  читает доказательства и в логах.
- **Удаляй устаревшие тесты:** на практике тесты получают приоритет над спеками;
  ручная фильтрация тестов — удаление устаревших и неэффективных синтетических —
  полноценный шаг.

**Взято:** всё, как правило качества канона, плюс третий класс тестов —
**target-тесты** — из доказательства ESEM 2026 ниже. Шесть каналов
(unit/contract, E2E/smoke, ожидаемый вывод, записанное воспроизведение,
браузер/снимок, производительность) — инструменты; spec/invariant/target — ось цели.

### Доказательство: ESEM 2026 — target-тесты с LLM-агентами

Jiayu Liu and Yanjun Wu, *Beyond Heuristics? Rethinking Targeted Unit Test Generation in
the Era of LLM Agents*, ESEM 2026, LIPIcs vol. 394, 47:1–47:21,
[DOI 10.4230/LIPIcs.ESEM.2026.47](https://doi.org/10.4230/LIPIcs.ESEM.2026.47).

- **Дизайн:** 210 реальных багов **runtime-исключений** в Java из 66 проектов. Агент
  получает кодовую базу с багом, тип исключения и место на уровне строки; он должен
  построить JUnit-набор, который вызывает это исключение в этой строке. Ни спеки, ни
  патча — только воспроизведение.
- **Результаты:** 89,5 % (Claude Code + GPT-5; 325,8 с, $1,09 за баг), 87,6 % (OpenHands
  + GPT-5), 65,2 % (OpenCode + DeepSeek-V3.2; $0,04), против UnitCon 49,6 %, EvoSuite
  39,4 %, Randoop 21,3 %.
- **Оговорки о качестве:** в ручной выборке из 90 успехов 5,6 % — вырожденные пути
  (искусственные входы вроде сырых null во внутренние методы), 16,7 % обходят
  публичные входные workflow и манипулируют приватными API или внутренними
  синглтонами, а 72,2 % имеют низкую семантическую ясность. Сгенерированные тесты
  структурно хрупче тестов разработчиков.
- **Режимы сбоя:** Insufficient Exploration 41,5 %, Inadequate Reasoning 25,5 %, Tool
  Misuse 14,0 %, Incorrect Focus 11,5 %.
- **Границы:** только runtime-исключения Java; авторы утверждают, что ключевые
  способности не зависят от языка, но логическим багам и багам утверждений может
  понадобиться контекст спеки, а баги конкурентности вне рамок.

**Что подтверждает статья:** target-тесты, сгенерированные LLM-агентами против
известного сбоя, гораздо эффективнее воспроизводят его, чем инструменты,
ориентированные на покрытие или эвристики; цикл — исследование кода → обратная связь
по исполнению → уточнение.

**Чего статья не подтверждает:** она не измеряет TDD, не сравнивает тесты, выведенные
из спеки, с target-тестами и **не сообщает 53 %**. Ближайшее число — 49,6 % у UnitCon.
«53 %» и утверждение, что обычные unit-тесты пропускают половину багов, — более
широкий аргумент оператора (возможно, из другого источника), и его нужно цитировать
отдельно. Базовые линии — инструменты генерации тестов, а не наборы TDD, написанные
разработчиками.
