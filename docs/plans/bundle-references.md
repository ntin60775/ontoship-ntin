# Справочники метода в бандлах

## Цель

Потребитель после установки получает методное знание, на которое скиллы
ссылаются в императивных шагах: процедуры запуска панели и онто-дока,
контракты ревью-ролей и правило качества едут в `references/` бандлов.
У свежей установки нет висячих ссылок скиллов на три справочника
`docs/` проекта; ссылки на канон `docs/decisions/ontoship-core.md` —
вне рамок юнита (см. «Рамки»).

## Готово

1. В бандлах `ship`, `onto-doc`, `testing` появились `references/` с
   методными секциями; шаги скиллов, которые в v0.3.0 указывали на
   `docs/reference/…` проекта, указывают на файлы бандлов — внутри
   своего бандла или на соседний относительным путём
   `../<бандл>/references/<файл>`. Доказательство: тест, который
   проходит по всем ссылкам на справочники в поставляемых скиллах и
   проверяет существование файлов на диске после установки обоими
   каналами.
2. Guard-фраза в каждом ссылающемся скилле: файл бандла — первоисточник,
   проект переопределяет его документом `docs/reference/<имя файла
   бандла>` — перекрытие привязано к имени файла бандла, не к имени
   KB-дока.
   Доказательство: якорные тесты контрактов с мутационными пробами
   (запрещённые формулировки, императив полной фразой, порядок шагов).
3. Паритет несущих: методная секция живёт в наборе носителей одного
   якорного теста — KB-док ntin называет файл бандла носителем методной
   секции, бандл-файл встаёт в этот набор рядом с уже существующими
   носителями. Доказательство: якорный тест паритета по образцу
   `tests/test_canon_sync.py` (расширение его набора носителей) с
   мутациями, чувствительными к регистру и переносам.
4. Оба канала установки несут `references/`. Установщик копирует бандл
   целиком (`scripts/install.sh`), раннер маппит каталоги бандлов целиком
   (`deploy.json`) — изменений механики не нужно. Доказательство:
   расширение `tests/test_install.py` + проверка состава после
   `install` раннера.
5. Граница в каноне: одна фраза в `docs/decisions/ontoship-core.md` —
   методное знание скиллов возится в их бандлах, KB проекта — проектное
   знание. Доказательство: фраза в каноне + правка носителей одним
   изменением, если канон её пересказывает.
6. Релиз v0.4.0: тег на origin, пин каталога. Доказательство:
   `ls-remote` тега, пин в `marketplace.json`, install по пину в чистый
   каталог — живая проба канала раннера.
7. Приёмка потребителя: `update` раннером в erp-demo
   (`/home/prog7/home/dev/work/erp-demo`, пин v0.3.0 → v0.4.0) и один
   живой панельный прогон на ближайшем готовом тикете bus-mapping-module
   (05) — панель стартует по процедуре из бандла, ни одна ссылка скиллов
   на три справочника не висит. Двойная роль: этот же прогон — приёмка
   тикета 05 erp-demo; приёмка их тикетов 06–07 идёт обычным порядком их
   юнита. Акт rollout `v0.3.0 → v0.4.0` записывается в consumer-registry.

## Рамки

- Раскладка владельцев (решение оператора, 2026-11-03): файлы в бандлах
  называются по смыслу, не по имени KB-дока —
  `ship/references/review-panel.md` («Ревью-панель по харнессам»
  `harnesses.md:67` и контракты ролей `review-roles.md:19,30`),
  `onto-doc/references/ontodoc-run.md` («Прогон онто-дока по харнессам»
  `harnesses.md:108`), `testing/references/quality-rule.md` (правило
  качества `testing.md`: артефакт доказательства 44, планка качества 123,
  классы 143, агентный цикл 158). Перекрытие проектом —
  `docs/reference/<имя файла бандла>`.
- В бандлы едут секции, переписанные стоять самостоятельно и без фактов
  ntin-репо (канон текстов: проектных фактов в скиллах нет).
  Исследовательские разделы остаются в KB ntin: «Доказательства»
  (`harnesses.md:35`), ESEM-нарратив и метрики (`testing.md:68,184`),
  «Регламент паков» (`review-roles.md:85`) остаётся в KB ntin — фактура
  контурных паков, метод её не несёт.
- Шесть ссылок v0.3.0 на три файла заменяются без изменения смысла
  шагов: `ship:55`
  (контракты), `ship:58` (запуск панели), `onto-doc:65` (прогон
  онто-дока), `onto-doc:71` (сверка карточки), `testing:11` (правило),
  `to-tickets:35` (артефакт доказательства).
- Механика поставки не меняется: бандлы копируются целиком обоими
  каналами, workflow не трогается.
- Ссылки скиллов на канон `docs/decisions/ontoship-core.md` — вне рамок
  юнита: названный пробел поставки, запись в «Что осталось» юнита идёт в
  тикете 03.

## Ограничения

- Одно правило — одна несущая текста на носитель: паритет сторожит
  якорный тест; replace-мутации пишутся по точному фрагменту носителя
  (урок тикета 02 onto-doc: регистр и переносы ломают replace).
- KB ntin не худеет: полные доки остаются в `docs/reference/`, kb-first
  поиск в ntin продолжает находить правило целиком; бандл несёт методную
  секцию.
- Управляемый блок init не расширяется: вход в метод доставлен в v0.3.0.
- Guard-фраза не подменяет поиск проекта: если проект написал свой
  `docs/reference/<имя файла бандла>`, скилл берёт его; бандл — источник
  по умолчанию, не единственный.
