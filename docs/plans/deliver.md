# deliver — поставка и обновление ядра в проекте, реестр потребителей

Спека юнита. Повод — оператор 2026-11-17: команда «деплой и обновление
[имя_проекта]» не маршрутизируется — у интента «поставить/обновить
OntoShip в проекте X» нет носителя (ни скилла, ни строки блока входа, ни
runbook). Это выстреливший названный пробел юнита entry-and-continuity:
«маршрутизация естественных запросов не доказана» — носитель фразы
[continue.md](../ops/continue.md) (хроника юнита); пробел остаётся
названным, словом оператора 2026-11-02 снята живая проба, не пробел.
Оператор формулирует интент произвольно близко по семантике; агент
должен понимать сразу, без гадания. Второй факт оператора: минимум 10
проектов под раскатку — учёт парка потребителей нужен с первого дня;
старый реестр мёртв (файл `.zcode/registry.local.json` снесён вместе с
ZCode-рельсами 2026-11-10, [continue.md](../ops/continue.md)).

Спека утверждена на план-гейте 2026-11-17 ask-проходом (вариант
«утвердить»). **Ревизия 2026-11-17** — по триажу гейта проекций
(решение 8 оператора «править всё по рекомендациям»; отчёт —
`tickets/deliver/00-projection-report.md`, 27 групп находок).

## Цель

1. Интент «поставить/обновить OntoShip в проекте X» маршрутизируется
   нативно: скилл `deliver` с description, несущим семантику поставки и
   обновления, плюс строка команды в блоке входа init.
2. Протокол поставки/обновления исполним и доказан: поиск проекта,
   канал, установка, init, `check: ok`, акт rollout, отчёт фактами.
3. Реестр потребителей возрождён как отдельный поставляемый скилл
   (репо `consumer-registry`, DSH-нативно): любой продюсер ведёт свой
   парк, ядро связано с ним только именем скилла и absence-поведением.

## Решения

Приняты оператором ask-проходом 2026-11-17 (раунды 1–5 фронтира,
гейт проекций, судьба находок).

| # | решение | отвергнутая альтернатива |
|---|---|---|
| 1 | Носитель интента — скилл `deliver` + строка «Команды» init-блока; полный протокол только в скилле, блок называет команду (паттерн `ship`) | runbook `docs/ops/` + строка блока без скилла (протокол вне каталога, маршрутизация только через блок) |
| 2 | Скоуп юнита — deliver + реестр одним юнитом; факт rollout пишется только в реестр (один носитель), в continue.md целевого проекта запись не делается | реестр отдельным юнитом (двойной флоу, окно без fleet-вида); только отчёт без записи (при 10 проектах учёт парка не покрыт) |
| 3 | Реестр — отдельный репо `consumer-registry`, DSH-нативное возрождение: свой `install.sh`, бандл несёт схему/валидатор/каркас, коннектор deliver→реестр по имени скилла с absence-поведением | опциональный бандл внутри ядра (новый концепт установщика, размыв границы канона); DSH host-плагин (профильный уровень против project-local данных, оверкилл для JSON+валидатора) |

| 6 | Доказательство маршрутизации — живая проба свежими сессиями на изолированном хосте (паттерн ctb04/tp07, живой GUI не перезапускается); матрица контуров и число сессий — в «Готово» 4 (ревизия по триажу G-1–G-3, G-10) | только каталог + якоря (не доказывает маршрутизацию — исходный пробел); проба в живом GUI (трогает рабочий профиль оператора) |

| 8 | Судьба находок гейта проекций: править всё по рекомендациям триажа одним проходом; ревизия спеки после план-гейта — этим решением оператора | выборочные правки; принятие риска (P1-находки делают критерии нечестными) |

Тривиальные решения агента (фильтр тривиальности, решение 23 канона;
обратимы, малое влияние, явных требований оператора нет):

- имя бандла — `deliver`; описание разводит deliver и init: deliver —
  весь акт поставки/обновления, init — только точка входа; description
  не содержит литералов парафраза «раскатай ядро в X» (ревизия G-24);
- methodContract не бампится — несущие нормы ведения не затронуты
  (канон «Границы», bump-правило);
- поиск проекта X: имя → реестр потребителей и соседние чекауты;
  не найден — ask пути, не угадывать;
- deliver запускает init после свежей установки и повторный init при
  обновлении (блок входа обновляется); install.sh сам init не запускает;
- канал при обновлении молча не меняется; смена канала — ask оператора;
- расхождение copy-установки: отказ установщика «copy differs» называется,
  удаление drifted-копии — только с подтверждения оператора; legacy-корни
  и выведенные бандлы установщик не трогает (warning);
- бандл реестра самонесущий: `SKILL.md`, `templates/` (схема, каркас,
  gitignore-строка), `scripts/registry_check.py` внутри каталога бандла;
  frontmatter скилла — DSH-идиома ядра (`name`, `description`);
- реестр ставится продюсером себе сам; deliver не ставит реестр
  потребителям;
- владение `.gitignore` построчное: пять строк init + строка реестра;
  init чужие строки не удаляет, реестр строк init не трогает;
  формулировку init до файловой эксклюзивности не усиливать (G-18);
- случай локальных правок внутри блока у потребителя владеет контракт
  init («внутренний текст отличается → замена + [WARN]», тесты init);
  отдельная проба не добавляется (G-23).

## Протокол deliver

Нормы протокола — тело скилла `deliver`; спека фиксирует контракт.

1. **Источник.** deliver исполняется там, где чекаут ядра доступен:
   `scripts/install.sh` лежит в корне репо ядра, не в бандле.
   Link-продюсер резолвит путь ядра из realpath бандла
   `.agents/skills/deliver`; copy-продюсер — ask оператора о чекауте
   ядра; молчаливого клона/remote нет (правило одного пути). Канал
   продюсера и путь использованного install.sh — в evidence (G-14).
2. **Поиск X.** имя → реестр потребителей и соседние чекауты; не найден
   — ask пути. Ask-нога в пробе без оператора не исполняется —
   названный пробел (G-1).
3. **Состояние.** `install.sh --check <X>` до обновления определяет
   состояние; warning установщика (legacy-корни, выведенные бандлы)
   deliver называет в отчёте до утверждения «поставлено»; `check: ok`
   не отменяет warning (G-16).
4. **Канал.** свежая установка — ask канала link/copy; обновление —
   тем же каналом, смена — ask оператора. Замена неверного симлинка в
   `.agents/skills/` — штатное действие установщика (relink), не
   деструктив (G-19).
5. **Установка/обновление.** install.sh соответствующего канала;
   drifted-копия — отказ «copy differs» называется, протокол
   останавливается на ask удаления (деструктив — оператор).
6. **Init.** после свежей установки и при обновлении — скилл init
   (идемпотентен; блок — только между маркерами).
7. **Акт rollout.** скилл реестра в каталоге — deliver загружает его и
   следует правилам: файла нет — старт ведения (решение 7), затем акт;
   скилла нет — запись не делается, пробел называется в финальном
   отчёте, fallback-записи нет.
8. **Отчёт фактами.** версия до/после, канал, вывод check, warning,
   акт или названный пробел — финальным сообщением сессии.

**Контракт акта** (G-6, G-7): `action` = `rollout` (свежая) | `update`
(обновление); `actor` = сессия deliver; `to`/`version` потребителя =
тег link-дерева, иначе `git describe` (dev+sha); для copy — прежнее
`consumers[].version`, без прежней записи — `unknown` с названным
пробелом; `from` = прежнее `consumers[].version`; `updated_at`
обновляется. deliver сверяет открытые followups (`done: false`) перед
поставкой по правилам скилла реестра и пишет followup «свежая сессия
потребителя» после обновления. `acceptance[]` deliver не заполняет —
акт оператора, названный пробел v1. deployed.json не заводится;
формулировки схемы о мёртвых носителях версии не правятся (вне скоупа).

## Готово

Каждый пункт доказывается названным носителем вместе с прочитанным
артефактом. Прогоны протокола (пункт 3) слиты с пробой маршрутизации
(пункт 4) — одна проба, без двойной цены (G-9).

1. **Бандл `deliver` в ядре.** `skills/deliver/SKILL.md` существует,
   несёт протокол и текст коннектора (G-5); description несёт семантику
   «поставить/обновить/деплой OntoShip в проекте»; массив `SKILLS`
   установщика — 11 бандлов, паритет носителей имён (install.sh, кортеж
   `tests/test_install.py`, `skills/README.md`) зелёный. Порядок
   selfhost: SKILLS/тесты/README → selfhost-установка (link) →
   `install.sh --check` — `check: ok` (G-26). Членство deliver в
   каталоге скиллов проверяется в текущей сессии после установки
   (каталог обновляется в сессии, G-15). Доказательство: прогон тестов,
   вывод установщика, каталог скиллов сессии.
2. **Строка команды в блоке входа.** Шаблон блока init несёт команду
   поставки/обновления со ссылкой на скилл `deliver`; selfhost-блок
   репозитория равен шаблону (повторный init, diff пуст после);
   пины `tests/test_skill_init.py` обновлены тем же срезом.
   Доказательство: якорные тесты, вывод повторного init.
3. **Протокол исполним.** Исполнитель — deliver (на базовом коммите
   скилла нет — критерий красный). Ноги протокола доказываются
   прогонами пункта 4: свежая установка link и copy, обновление link
   (baseline `v0.7.0` → срез), отказ drifted-копии назван и остановлен
   на ask (удаление — нога оператора, в пробе не исполняется —
   названный пробел), идемпотентный init. Предусловие temp-проектов:
   `git init` + базовый коммит до первого init — пустой diff иначе
   ничего не доказывает (G-9). Diff целевого проекта после поставки —
   только `.agents/` и файлы init; continue.md после init не изменён
   (G-22). Доказательство: логи и транскрипты пробы пункта 4.
4. **Семантическая маршрутизация доказана.** Изолированный хост —
   копия профиля web без team/stack-строк (паттерн ctb04), свой порт;
   env-факты старта — [continue.md](../ops/continue.md) («Факты
   окружения», node вне PATH); механика создания и ведения сессий —
   прецеденты tp11/ctb04 (ссылкой, не пересказом). Участники: чекаут
   ядра — worktree среза на зафиксированном sha (источник канала);
   продюсер P — temp-проект под `/tmp` вне git-деревьев ядра,
   собственный git-репозиторий; потребитель X — отдельный свежий
   temp-проект, соседний чекаут, находимый поиском по имени (G-1,
   G-11). Матрица — пять свежих сессий, на каждый парафраз своя
   сессия (G-3):

   | контур | продюсер | сессий | парафраз | нога протокола |
   |---|---|---|---|---|
   | K1 presence | ядро link + реестр + init | 3 | «деплой и обновление X» (литерал блока); «поставь онтошип в X»; «раскатай ядро в X» (без общих слов с носителями) | свежая link; обновление copy с refusal; обновление link с baseline `v0.7.0` |

   Парафразы не содержат литерал строки блока, кроме названного
   литерала K1 (блок-маршрут доказывает он; description-маршрут —

   установка из дерева `v0.7.0`, созданная драйвером пробы до сессии;

   релизного дерева: ядро — 11 бандлов, `check: ok`; реестр — один

   description deliver — повторная проба от тега либо названный

8. **KB и контур зелёные.** Спека, индексы (`docs/plans/README.md`,

   `lint --strict` чист; полный набор тестов ядра зелёный; красные
   пробы критериев: ядро — на базовом коммите юнита, реестр — на
   `v0.2.0`. Доказательство: прогон, `git diff`, красные логи.

## Рамки

- Скоуп v1 — только ядро OntoShip. Паки стандартов, team-бандл и
  1C-стек — их контуры (канон «Границы»); deliver их не ставит и не
  обновляет.
- Реестр — producer-side: продюсер ведёт своих потребителей. deliver
  не ставит реестр потребителям и не требует его наличия.
- Файл реестра машино-локальный, вне git, между машинами не переносится
  (семантика контракта `consumer-registry/1` сохранена). **Риск
  рецидива**: снос `.agents` уничтожает реестр, как снос `.zcode`
  уничтожил старый; бэкап/экспорт вне v1, потеря = ручное
  перенаполнение; предупреждение — в шаге старта ведения (G-27).
- Схема `consumer-registry/1`: неизменны поля, структура, `const`
  версии, required-наборы; путевые литералы описательного текста
  схемы/каркаса и строка gitignore.snippet правятся под решение 4
  (G-8). Журналы append-only: отменённый шаг — новая запись, не правка
  старой.
- `acceptance[]` deliver не заполняет (акт оператора) — названный

## Ограничения

Точки остановки ship и правила прогона:

- Неразобранное расхождение ожидание/факт — остановка ship, вопрос
  оператору ([testing.md](../reference/testing.md), «Артефакт
  доказательства»).
- Деструктив у потребителя (удаление drifted-копии, legacy-корней,
  выведенных бандлов) — только с подтверждения оператора; установщик
  их не трогает, deliver называет и спрашивает. Замена неверного
  симлинка в `.agents/skills/` — штатный relink установщика, не
  деструктив (G-19).
- Живой GUI оператора не перезапускается; пробы маршрутизации —
  изолированный хост (копия профиля без team/stack-строк), уборка
  runtime/credential после пробы обязательна и доказывается записью
  (Готово 4, паттерн ctb04).
- Link-проба несёт поколение клона на момент установки: sha и путь
  link-дерева фиксированы в install-логе; после любой правки дерева
  проба недействительна, check перезапускается; дрейф поколения
  назван (G-12, уровень core-team-boundaries).
- Реестра нет — запись не делается и пробел называется; fallback-записи
  в другой носитель нет (решение 2, правило одного пути).
- Панель красная после одного прохода правок или маршрут недоступен —
  остановка по правилу ship, вопрос оператору; автоприёмка на таком
  контуре не делается.
- Теги — после merge соответствующего контура; тег на origin до merge
  запрещён.
- Правка блока входа у потребителя при обновлении — только между
  маркерами ontoship по контракту init; текст вне маркеров не трогается.
